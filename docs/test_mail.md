# 管理者によるテストメール

通常当選・繰り上げ当選・第1回／第2回リマインドのある新方式（confirmed）イベントで使用する。
当選メール設定またはリマインド画面の「テストメール送信」から、種類・対象申込・承認済み宛先を選び、プレビュー後の最終確認で1通配送する。
既存の正式メール生成関数・メール配送基盤を使用する。件名先頭の【テスト送信】と本文冒頭の注意文だけを付加する。

## 宛先と権限

システム管理者がイベントごとに社内宛先を最大10件承認する。イベント管理者は承認済み宛先だけに配送できる。
4本のAPIはFirebase AuthとApp Checkを必須とする。取得・プレビュー・送信は対象イベント管理者以上、許可リスト変更はシステム管理者のみ。
受付スタッフ・他イベント管理者・未認証者には公開しない。クライアントからのFirestore直接アクセスは既存Rulesのデフォルト拒否が適用される。

## 正式データとの分離

使用する保存先は `testMailPolicies/{eventId}`、`testMailDeliveries/{contentHash}`、`testMailLimits/{eventId}` だけ。
正式イベント設定・参加者・資格・QR・受付・sendJobs・mailDeliveriesには書き込まない。
リマインドの予定日時・正式文面が未設定でもテストできる。仮文面はリクエスト中だけに存在し、件名・冒頭本文に「テスト送信・正式文面ではありません」が必要。
既に正式文面がある回では仮文面の上書きを拒否する。

実参加者のQR・URLは既存の有効なものを使用する。テスト受信者が受付に使用してはいけない。
架空申込は保存しない。QRは `JM_QUICK_TEST_ONLY_NOT_A_RECEPTION_QR`（URLではない）、参加証リンクは example.invalid。
架空の申込日時・時間・人数を使うことを選択画面に明示する。
資格追加通知は対象参加者と追加した取込回を選び、正式生成処理が今回の資格だけを表示する。

## 配送保証と限界

サーバー再生成した本文・宛先・種類のSHA-256と確認済みプレビューを照合する。
送信前にFirestore transactionで配送記録を一度だけ取得し、同時にイベントあたり毎時10通の制限を適用する。
同一イベント・種類・宛先・生成内容の再送は常に拒止（既存の配送結果を返す）。成功・失敗・結果不明を問わず自動再試行しない。
ネットワーク切断後も開始済みの単発送信はサーバー上で実行する。サーバー中断などで結果を保存できなければ2分後に画面上で結果不明と表示し、再送しない。
これは少なくとも1回の保証ではなく、重複を避ける設計。未配送が疑われても結果不明記録を消して再送しない。
正式配送の定期処理には接続しない。

## 本番反映

新規4 FunctionsとHostingのみ。既存Functions・Rules・Indexes・Secret・送信元の変更は不要。
許可リストは本人認証したシステム管理者の正式APIを通して承認する。承認済みアドレスをソースやログへ複製しない。
本番検証時にsendConfirmedTestMailを実行しない。実送信は管理者による宛先・件数・本文の最終承認後だけ行う。
